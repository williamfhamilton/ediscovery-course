Why this matters

A hash value is a short fixed-length fingerprint computed from every byte of a file. Change one character, one space, one pixel — and the hash changes completely. That makes hashing the standard way to prove two files are identical without comparing them byte by byte, to deduplicate a production, and to show that a document wasn't altered after it was collected.

ESI protocols routinely specify which hash algorithm the parties will use (commonly MD5 or SHA-256) and at what level — file-level, or message-level for email family groups.

Two kinds of metadata

System metadata lives outside the file, in the file system: the "Last Modified" date your computer reports, the file name, the file size. It travels with the storage location, not the content — copy a file to a new drive and its system metadata can change even though nothing inside it did.

Embedded (application) metadata lives inside the file itself, written there by the software that created it: author, creation date, revision count, last-saved-by. It travels with the file wherever it goes — which is exactly why it can surface things a producing party didn't intend to disclose.

Classroom use
💬 Discussion prompts
  1. Two versions of the same document have different hash values. What does that tell you — and what does it not tell you — about what changed?
  2. A file's embedded "Created" date is earlier than the system "Last Modified" date your computer shows. Why might that be, and when would the gap between them matter in a spoliation dispute?
  3. A produced document's metadata shows "Last Modified By" as someone who left the company two years before the document was supposedly created. What would you want to investigate?
  4. If this tool can't find embedded metadata in a file, does that mean the metadata doesn't exist? What would you do next in an actual matter?
  5. Would you rather negotiate an ESI protocol that specifies MD5, SHA-256, or both? What's actually at stake in that choice?
Limitations, on purpose
This tool reads metadata using straightforward, unencrypted file structures — the same docProps XML inside a Word file, the same /Info dictionary in a PDF, the same EXIF block in a JPEG. It won't see everything a forensic tool like EnCase, FTK, or ExifTool would surface: some PDFs store metadata in compressed object streams this tool doesn't decompress, and metadata can be scrubbed before a file ever reaches you. That gap is itself worth sitting with — deciding when a quick check is enough and when a matter calls for real forensic tooling is a judgment call you'll make constantly in practice.
